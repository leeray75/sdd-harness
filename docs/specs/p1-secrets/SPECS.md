# p1-secrets

## Problem

The spike gets its provider key from the app's environment (`HARNESS_SPIKE_API_KEY`), and main passes it to the agent's environment. The PRD requires keys to live in the OS keychain through `safeStorage` and never reach logs, sessions, exports or files. Nothing stores keys yet, and nothing redacts them. Main's log writes whatever it is given, including every line of agent output it forwards. Every adapter that follows (`p1-provider-interface`, `p1-openai-compatible`) needs a safe place to read keys from.

## Goals

- **G1:** A main-process secret store that keeps provider keys only as `safeStorage` ciphertext in app data, and refuses to save when real encryption is unavailable.
- **G2:** A redaction helper that every line main writes goes through: main's own log lines, router logs, error paths and forwarded agent output.
- **G3:** A stored key reaches a model call through a per-run `model-key` message from main to the agent. The agent holds the key in memory only, never in its environment (recorded as D25).
- **G4:** The spike runs on a key from the store, with a dev-only `pnpm secrets:*` script to set, list and delete keys before the settings UI exists.
- **G5:** Tests prove a sentinel key never appears in logs, errors or test output, and the documentation matches the code when the work lands.

## Non-goals

- Any settings UI for entering keys (Phase 8).
- The provider interface and adapters (`p1-provider-interface`, `p1-openai-compatible`).
- Cloud platform credentials (Bedrock, Azure, Vertex).
- Exports and sessions, which don't exist yet; the redaction helper is written so they can use it later.
- Escaping control characters in agent-supplied strings in logs (Phase 2 follow-up).
- Changing the live suite: `pnpm test:live` runs the loop outside the app and keeps reading `HARNESS_SPIKE_API_KEY` from its environment.
- A loopback proxy, or model calls made from main.

## Acceptance criteria

- **AC1 (store):** `src/main/secrets/store.ts` exports a store built from injected dependencies: a crypto object (`isEncryptionAvailable`, `getSelectedStorageBackend`, `encryptString`, `decryptString`), a file path, the platform, a weak-backend override flag and a redactor. It has `save(name, value)`, `read(name)` (returns the value or `null` when absent), `delete(name)` and `listNames()`. Names must match `^[a-z0-9][a-z0-9-]{0,63}$`, and values must be non-empty strings of at most 4,096 characters; anything else throws a clear error. The file is JSON `{ "version": 1, "entries": { "<name>": "<base64 ciphertext>" } }`, written atomically (a temp file in the same directory, then a rename) with mode `0o600`. `delete` and `listNames` never decrypt. A unit test with a fake crypto (reversible, but not identity) and a temp dir shows that after `save`, neither the file nor any other file in the directory contains the plaintext value, and that `read` returns it.
- **AC2 (refusal):** `save` throws an error that says encryption is unavailable and names no value when `isEncryptionAvailable()` is false, or, on `linux`, when the backend is `basic_text` or `unknown` and the override is off. In each case nothing is created or changed on disk; a unit test checks the directory listing and contents before and after. With the override on, `basic_text` is accepted. `read` of an entry whose ciphertext cannot be decrypted throws an error that names the entry but contains neither ciphertext nor plaintext. No error message from the store contains a value or ciphertext.
- **AC3 (Electron wiring):** `src/main/secrets/electron.ts` builds the store from Electron's `safeStorage`, `app.getPath('userData')/secrets.json`, `process.platform`, `HARNESS_ALLOW_WEAK_SECRETS === '1'` from main's environment, and the shared redactor. It is used only after app ready. `HARNESS_ALLOW_WEAK_SECRETS` is not passed to the agent.
- **AC4 (redaction):** `src/main/secrets/redact.ts` exports a redactor with `register(value)` and `redact(text)`, and a process-wide instance. `redact` replaces each of these with `[redacted]`: every registered value, wherever it appears; the token after `Bearer ` (case-insensitive); the value of an `Authorization` or `x-api-key` header, written as `name: value` or `"name":"value"`, case-insensitive; and `sk-` or `sk-ant-` followed by at least 20 characters from `[A-Za-z0-9_-]`. Registering an empty or whitespace-only value does nothing. Unit tests cover each rule, a value appearing several times, a value inside JSON, and near-misses that stay unchanged (`sk-short`, the word `Bearer` with no token).
- **AC5 (store registers):** `read` registers each value it returns with the redactor before returning it, so any later log line containing it is redacted. A unit test proves this.
- **AC6 (logger):** `log.info`, `log.error` and `log.forward` in `src/main/log.ts` pass each line through the process-wide redactor before writing. A unit test with stubbed `process.stdout.write` and `process.stderr.write` shows that a registered sentinel and a `Bearer <sentinel>` string are absent from what is written by each method, including a forwarded agent line.
- **AC7 (protocol):** `src/shared/agent-protocol.ts` adds a main-to-agent message `{ type: 'model-key', key: string | null }` with `key` at most 4,096 characters when it is a string. `validateMainToAgentMessage` accepts it and rejects a missing `key`, a non-string non-null `key` and an oversized `key`. No rejection reason from either guard contains a field value. Unit tests cover each case and use a sentinel to check the reasons.
- **AC8 (env):** `HARNESS_SPIKE_API_KEY` is removed from the agent's spike variables, so `agentEnv` passes no key variable even with `HARNESS_AGENT_SPIKE=1`. The existing env tests are updated to show `HARNESS_SPIKE_API_KEY` is dropped with the flag on and off, and `HARNESS_ALLOW_WEAK_SECRETS` is dropped.
- **AC9 (host):** When `HARNESS_AGENT_SPIKE=1`, main, after the agent's pong, reads the `spike` entry from the store and sends `{ type: 'model-key', key }` once per agent process, with `null` when the entry is absent. If the store throws, main logs a redacted line saying the key could not be read and sends `null`. Without the flag, no `model-key` message is sent. A pure function, unit tested with a fake store, decides the message, and `host.ts` calls it.
- **AC10 (agent):** With `HARNESS_AGENT_SPIKE=1`, the agent starts the spike when it receives `model-key`, not on the ping, and only once per process. It builds its `openai` client from that key, or from the existing no-key placeholder when the key is `null`. The agent no longer reads any key from its environment. It never writes the key to stdout or stderr. Without the flag, a `model-key` message is ignored, with a log line that does not contain the key. The self-check is unchanged.
- **AC11 (SDK errors):** A unit test drives the agent loop with a sentinel key through an injected `fetch` that (a) returns a 401 whose body echoes the sentinel and the `Authorization` header, and (b) throws an `Error` whose message contains the sentinel. In both cases the loop's error, passed through the agent's error naming (moved to a small exported helper in `src/agent/`), and through main's redactor, contains no sentinel. A router test pushes a sentinel through a tool runner failure and the router's log lines, and the sentinel is absent from both.
- **AC12 (dev secrets mode):** When the app is not packaged and starts with `--harness-secrets=set|delete|list` (with `--harness-secret-name=<name>` for set and delete), main creates no window and starts no agent. After ready it runs the store call, prints only the operation, the name and `ok` or a redacted error, and quits with code 0 on success and 1 on failure. For `set`, main receives the value over a one-shot local socket whose address is given with `--harness-secret-pipe=<address>` (revision 1: Electron's main process gets no stdin on Windows). The address is a named pipe `\\.\pipe\sdd-harness-secret-<32 random hex characters>` on Windows, or `<private temp dir>/s.sock` on macOS and Linux, where the private dir is created with `mkdtemp` and mode `0o700`. Main connects once as a client with Node's `net` module, reads until the server closes the connection (at most 4,096 characters, with a 10 s timeout), and never logs what it reads. A missing or invalid address, a connection error, a timeout or an oversized value is a failure, exit 1, and nothing is written. The address is not secret and may appear on the command line; the value never does. In a packaged app these switches are ignored. `scripts/secrets.ts` (run as `pnpm secrets:set <name>`, `pnpm secrets:list` and `pnpm secrets:delete <name>`) builds the app if `out/` is missing, prompts for the value with hidden input when its own stdin is a TTY (or reads its own piped stdin, trimming one trailing newline), and refuses an empty value. It starts the socket server, accepts exactly one connection (later connections are closed with nothing sent), writes the value and closes. It then starts Electron in the secrets mode with the address, waits for it to exit, closes the server and removes the private temp dir. The value never goes on the command line, in an environment variable or in a file. The pure parts of the mode (switch parsing, the value checks and the output lines) have unit tests, and so does reading a value from a local socket server in a test, including the timeout and oversized cases.
- **AC13 (spike e2e):** `tests/e2e/spike-agent.spec.ts` uses a temp user-data dir (`--user-data-dir=<tmp>`, checked during the build to set `app.getPath('userData')`). It first seeds the `spike` entry with a sentinel through the dev secrets mode, with `HARNESS_ALLOW_WEAK_SECRETS=1`. It then starts the app with `HARNESS_AGENT_SPIKE=1` and without `HARNESS_SPIKE_API_KEY`. The replay server records the `Authorization` header of each chat request. The test asserts that every request carried `Bearer <sentinel>`, that `read_file` ran and the spike finished as before, that the sentinel appears nowhere in the app's stdout or stderr (from both runs), and that `secrets.json` in the temp dir does not contain the sentinel.
- **AC14 (docs):** `docs/decisions.md` has D25 (key storage and delivery: safeStorage store in main, `basic_text` refused with a test-only override, per-run `model-key` message, agent holds the key in memory only, redaction of all main output, with the alternatives not chosen). D19 is amended in the existing "Amended:" style for the `model-key` message. `CHANGELOG.md` has `[Unreleased]` entries. The spike sections and command lists in `README.md` and `CLAUDE.md` describe `pnpm secrets:set spike` and say `HARNESS_SPIKE_API_KEY` is read only by `pnpm test:live`. The `p1-secrets` follow-up in `docs/phases/phase-01-progress.md` is struck as done. A grep of `docs/` (except `docs/specs/`), `README.md`, `CLAUDE.md`, `src` and `tests` finds no statement the change made false about `HARNESS_SPIKE_API_KEY` reaching the app or the agent.
- **AC15 (full check):** `pnpm typecheck`, `pnpm lint`, `pnpm format:check` and `pnpm test` pass, and `pnpm e2e` passes locally on Windows. Existing tests change only where this spec changes behaviour.

## Open questions

- 2026-11-19, revision 1: On Windows 11 the unpackaged app in secrets mode received an empty stdin for both `echo value |` and a `< file` redirect (Electron's main process runs as a GUI-subsystem app), so AC12's stdin handoff cannot work. Decided: the dev script hands the value to main over a one-shot local socket (a random named pipe on Windows, a socket in a private `0o700` temp dir on macOS and Linux); only the address is passed on the command line, and the value never touches disk. `--user-data-dir` was confirmed to set `app.getPath('userData')`, so AC13 is unchanged. Not chosen: a one-time private file (the plaintext touches disk briefly); an inherited fd 3 pipe (unverified on Windows); a dev-only window with a hidden input (adds renderer and preload code).
